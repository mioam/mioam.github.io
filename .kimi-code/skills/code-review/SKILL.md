# 代码审阅助手（Code Review Guide）

## 适用范围

本 skill 用于引导用户逐文件审阅项目代码。每次只聚焦一个文件，由浅入深：先理解代码，再给出建议，最后结合项目结构讨论影响。

## 启动流程

1. 询问用户本次想审阅哪些文件或模块。若用户未指定，则按项目依赖关系给出推荐顺序。
2. 确定用户当前项目相比上次审阅的改动。
3. 创建或更新审阅进度文件（默认 `review-progress.md`），记录：
   - 已审文件
   - 当前待审文件
   - 待审清单与推荐顺序
4. 使用 `TodoList` 建立/同步审阅任务，确保始终只有一个 `in_progress` 项。
5. 若涉及 README、AGENTS.md 等文档更新，**在审阅开始时先征求用户同意**。

## 单次审阅步骤

针对每一个待审文件，按以下结构输出：

### 1. 文件定位

- 文件路径
- 在项目中的职责一句话概括

### 2. 代码解析

- **做什么**：该文件解决了什么问题、承担什么角色。
- **用了什么**：关键依赖、框架 API、设计模式、类型定义等。
- **有哪些函数/组件/模块**：列出主要导出、函数签名、props、emit 等，必要时简述参数与返回值。

### 3. 审阅建议

分四类给出：

- **好的地方**：符合项目约定、设计优雅、可维护性高的点。
- **不对/有风险的地方**：明显 bug、类型错误、性能隐患、安全漏洞、违背项目约定（如 AGENTS.md）。
- **可以改进的地方**：非阻塞性优化、可读性提升、边界情况处理。
- **跳出单个文件看项目结构**：该文件与周边模块的耦合、是否应迁移到 shared、是否破坏插件隔离、是否影响路由/构建/部署。

### 4. 交流与修改

- 先让用户看完意见，再询问是否需要修改。
- 用户可选择：
  - 自己改（此时只更新进度/todo，不改文件）
  - 让助手改（使用 Write/Edit 工具执行）
  - 跳过，继续下一个
- 若用户说"按这个改"，助手使用 Write/Edit 工具修改文件。
- **助手修改文件后，必须先将改动结果展示给用户，等用户确认改得对不对，不要立即更新进度。**

### 5. 确认最终版本

- 用户确认文件已最终定稿（例如说"改好了"、"没问题"、"就这样"）后，再：
  - 在 `review-progress.md` 中勾选该文件
  - 将 `TodoList` 中该任务标记为 `done`
  - 将下一个待审文件标记为 `in_progress`
- 如果用户对修改结果还有意见，返回步骤 4 继续调整。
- 在用户确认之前，不要提前标记完成，也不要进入下一个文件。

## 文档更新

如果审阅过程中发现 README、AGENTS.md、review-progress.md 等文档需要同步更新：

- **先征求用户同意**："是否需要我同步更新 XX 文档？"
- 得到明确同意后，再使用 Write/Edit 工具修改。
- 更新后简要告知改动点。

## 风格约束

- 回复使用中文（代码、路径、接口名保持英文）。
- 避免一次性审阅多个文件，保持单文件聚焦。
- 引用代码时使用具体行号或片段，不要泛泛而谈。
- 提出的每个问题尽量附带可执行的修改方案。
- 尊重项目已有约定（如 AGENTS.md、.prettierrc），不要轻易建议引入新库或大型重构。
